## Previous Local Work — v1.179.0 — The data layer tells two answers apart (NOT deployed)

**P0.4, P0.5 and P0.6 of the V2 programme.** No business logic, no API, no database, no calculation, no visual change. One deliberate behaviour change, named below.

**P0.4 — the remembered-view layer.** `lib/cached-api.ts` is what every remembered view reads through: the dashboard's money, the roster, the hotel directory, Hankei's queues. It fetched from an effect and pushed each part of the answer into component state with a synchronous setState. The warning was the least of it. **It could not tell two answers apart:** two requests for the same view — a mount and a save's refresh — settled in whichever order the network chose and **the last to arrive won**, so an older answer could overwrite a newer one on screen AND in the cache, where it survived a reload. **A request begun as one person could land after another signed in on the same phone** and be written under the new person's key.

Three facts that are external to React are now read as such: the cache is an external store (`useSyncExternalStore`), so a remembered view is read DURING RENDER and paints on the first frame; the in-flight registry is a second store, so two cards on one path share ONE request; only the outcome of the last settled request is React state, set from a promise callback and never synchronously from an effect. Every request carries a sequence number, the account it began in and the cache generation it began in, and refuses to apply if any has moved. An explicit `refresh()` never joins a request that predates the save it is refreshing for. `getSnapshot` returns **a string**, never a parsed object, and is pure — the old reader deleted an expired entry while reading it, a write during render. Two render-time ref writes (`use-live-refresh.ts`, `record-detail.tsx`) are now `useEffectEvent`; `offline-banner.tsx` reads the connection as a store. **Sign-out empties the screen immediately** rather than leaving the previous person's figures painted.

**The one behaviour change:** a card whose `enabled` goes true → false reports `data: null` instead of keeping its last value. Every call site passes `path: null` alongside `enabled: false`, or a role flag constant for the session, so nothing on screen changes — and for a role-gated card, forgetting is the safer direction.

`tests/cached-api.mjs` (45 checks) RUNS the module against a strict hooks runtime, a localStorage with a real quota and an `api` whose every response the test settles by hand. **17 of its checks fail against the previous code**, including both money-relevant races.

## Previous Local Work — v1.177.1 — The queue tells the truth (NOT deployed)

**A data-integrity fix, released alone, ahead of the V2 programme.** No interface change.

`lib/outbox.ts` `enqueue()` returned `ok !== undefined || true` — **true for every input.** `tx()` resolves the IndexedDB *request's* result and a `put` has no result, so the check could never be true and the `|| true` hid that it never was. When IndexedDB was unavailable (Safari private browsing, storage pressure, a locked database) the punch was **dropped** and `lib/api.ts` still returned `{ ok: true, status: 202, queued: true }` — so the person read *"Kept — no signal. Sent the moment you are back online."* **Nothing was kept.** It surfaced weeks later as a missing attendance record and a wrong payslip: exactly the failure this file was written in v1.105.0 to prevent.

Beside it, a queued write that came back **5xx was removed and never retried**, on the reasoning that the idempotency key would only replay a stored answer. The worker does the opposite **deliberately** and its own guard has always said so — *"a 5xx is not stored, so the retry really retries"*. A server error usually means the write never landed. `attempts` was written on every failure and **never read**: no cap, no backoff, no end.

Now: `txOk()` reports whether the transaction COMPLETED and the row is **read back** — both must hold before `enqueue` returns true. `park()` returns `{ ok: false, dropped: true }` when the device could not keep it, and `reportDropped()` raises it through the same surface that already shows a refused write, so **every caller is covered by one report site**. The punch no longer falls through to "Location needed" (blaming GPS for a storage failure); it says *"Not saved — nothing was recorded."* A 5xx is retried with doubling backoff (30s → 8m), skipped while not due, and after **6 attempts** the queue stops and SAYS it stopped rather than looping.

Verification for `v1.177.1`: `tests/outbox.mjs` 76 → **86 checks**, ten of which **run the queue for real** against an in-memory IndexedDB rather than reading the source — the original bug was invisible to a source read because the shape looked right.
