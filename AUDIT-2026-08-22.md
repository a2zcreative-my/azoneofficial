## 2. Blockers

### B1 — A mid-flight failure permanently loses a sale, and tells the store it was applied
**`worker/src/bridge.ts:64-69`, `:86-113`, `:133-138`** · *mine, v1.36.0*

The movements handler writes four separate statements per movement with no transaction. The first inserts `bridge_events` with `outcome='pending'`. If anything fails after that insert and before the stock update — a D1 blip of exactly the kind `index.ts` already documents as routine — the catch leaves the id out of all three response lists, which is correct: silence means the store retries.

**But on the retry, `ON CONFLICT DO NOTHING` changes zero rows, so the code answers `ignored`.** The spec defines `ignored` as *"you had already applied this event_id"*, so the store marks it **delivered and stops retrying**. The pieces left the shop, the count never moved, and the movement can never come back.

It is also invisible: `bridgeHousekeeping` only prunes `applied`; the health card counts only `applied` and `unknown_sku`; nothing in the codebase ever transitions a `pending` row. My own migration comment says the column is `'applied' | 'unknown_sku'` — I did not model the state I created.

The comment I wrote at `:135-137` ("the ON CONFLICT gate makes the retry safe whether or not the event row survived") is exactly backwards.

**Fix:** make the whole movement atomic. Replace the read-then-write with one guarded statement — `UPDATE inventory_items SET stock = MAX(0, stock + ?) … RETURNING stock` — and apply the event insert, the stock update and the ledger row in a single `db.batch()`. Then `pending` cannot exist. Where a `pending` row is found on conflict, treat it as a **first attempt**, never as `ignored`. This fix also closes M1 below.

### B2 — Every ELFIA sale's cash and ledger entry fails silently, forever
**`worker/src/bridge.ts:268-274`** · *mine, v1.38.0*

`cashflow_entries.created_by` is `INTEGER NOT NULL` (`0071_erp_core.sql:70`). I bind `NULL`. Verified against the real cumulative schema:

```
NOT NULL constraint failed: cashflow_entries.created_by
```

So on every paid web order: the insert throws → my empty `catch { /* pre-0071 */ }` swallows it (mislabelled — it fires on a fully-migrated database) → `postJournal` sits after the throwing statement in the same `try`, so the GL entry never posts either → and `paid_seen_at` was already stamped **before** the try, so the order is never reconsidered.

Cash flow and the general ledger would under-report **every single web sale, permanently, with nothing logged.**

**Fix:** bind a real integer (`0` = system, matching what I already pass to `postJournal`), stamp `paid_seen_at` **after** a successful booking, and replace the silent catch with `logError`. A catch that hides a schema violation is worse than no catch.

### B3 — Any signed-in staff member can download the officers' signatures
**`worker/src/staff.ts:5853-5860`** · *mine, v1.38.0*

```ts
const sigServe = path.match(/^\/signature\/((?:ceo|coo|cco|hr-admin|sales-marketing)-sign\.png)$/);
if (sigServe && method === "GET") {
  const obj = await env.MEDIA.get(`private/signatures/${sigServe[1]}`);
```

**No `can()` call, no role check, no audit row.** The only gate is "authenticated and not a customer". So `editor`, `marketing` and `live_host` — roles that cannot open a single sales document — can fetch the CEO's real handwritten signature at full fidelity, leaving no trace.

I narrowed the leak from *the entire internet* to *anyone with a staff login*, then wrote a comment claiming it was restricted to "the people who could already print the signed documents", which is false for three of the roles it admits. And `tests/no-public-signatures.mjs` only asserts the route **exists** — it cannot fail on this.

**This needs your decision, because the correct fix is not a one-liner.** Ordinary staff legitimately print their *own* approved leave and claim forms, which carry the approvers' signatures. So a blanket role restriction would break that. The right shape is **document-scoped access** — `GET /staff/leave/:id/signature` verifying the requester owns or may approve that document — mirroring how the public route is scoped by share token. Interim option: restrict the role-scoped route to `sales`/`finance`/`exec_view`/`hr_manage` and move leave/claim form printing onto the document-scoped route in the same release. See [D-1](#5-decisions-i-need-from-you).

### B4 — A half-applied migration wedges the entire API deploy pipeline
**`worker/migrations/0075_bridge_pricing.sql:14`, `0076_bridge_movements.sql:62`**

Both files do `ALTER TABLE … ADD COLUMN` (not idempotent — SQLite has no `IF NOT EXISTS` for columns) **followed by** backfill and index statements. Re-run behaviour, measured:

| File | Re-run | Cause |
|---|---|---|
| 0075 | **FAIL** `duplicate column name: bridge_enabled` | ALTER mid-file |
| 0076 | **FAIL** `duplicate column name: sku_key` | ALTER mid-file |
| 0077 | OK | all `IF NOT EXISTS` |
| 0078 | OK | converges, second run matches 0 rows |

If execution stops after the ALTER but before the trailing statements, wrangler never writes the ledger row, the next `d1 migrations apply` replays from statement 1 and dies. `deploy-api.sh` runs under `set -e`, so **every subsequent automatic API deploy aborts before `wrangler deploy`**. One bad half-apply and the pipeline is stuck until someone hand-edits a migration or hand-inserts a ledger row.

Worse for 0076 specifically: if the ALTER lands but the `UPDATE … SET sku_key` does not, every item has `sku_key = NULL`, so **every inbound movement is answered `unknown_sku`** and the store stops retrying — silent, permanent under-deduction.

**Fix:** split each into ALTER-only and data-only migrations, or make each statement individually replayable. Add a guard asserting no migration mixes a non-idempotent ALTER with trailing dependent statements.

### B5 — Nothing is deployed, and the emergency path is now broken too
- `origin/main` is v1.34.0. The entire bridge — four migrations, three source files — is **unpushed**. `package.json` 1.38.1 and today's fix are **uncommitted**.
- The live API is **1.32.1**, one release behind even the pushed head. Your `azoneofficial-api` Workers Build connection either was never completed, or has failed every time since. `AUTO-DEPLOY.md:169` documents the trap: a CLI deploy requires disconnecting the repo, "and **reconnect it afterwards** — otherwise automatic deploys stop and nobody notices."
- **`DEPLOY.bat` now hard-exits**: it asserts `package.json` is `1.34.0` and aborts otherwise (`DEPLOY.bat:63-73`). The manual fallback for a broken pipeline does not run.
- `npm run ci` at the repo root **does not build or deploy the worker at all** — it typechecks the site, runs guards, and builds `out/`. A green website build publishes zero API changes.

**Fix:** diagnose the API worker's build in the Cloudflare dashboard before pushing anything; update `DEPLOY.bat`'s version gate; add a post-deploy assertion that the live `version` matches the built one (today `deploy-api.sh` curls health and pipes through `|| true` — a deploy that published nothing exits 0 and looks identical to a good one).

## 6. Remediation plan

Sequenced so each release is independently shippable and independently verifiable. **Nothing here is built yet — this is for your approval.**

### v1.39.0 — Bridge correctness (blockers + M1–M10) · *before the store is pointed at us*

1. **Atomic movement application.** One `db.batch()` per movement; `UPDATE … SET stock = MAX(0, stock + ?) … RETURNING stock`; `pending` eliminated as a state. On conflict, read the existing outcome — `pending` means retry, never `ignored`. *(B1, M1)*
2. **Cash booking fixed.** Real `created_by`, `paid_seen_at` stamped only after a successful booking, `logError` instead of a silent catch, and a **unique index on `cashflow_entries.ref` and `journal_entries.ref`** so the database enforces post-twice-book-once rather than a check-then-insert race. *(B2, M2)*
3. **Poller hardening.** Cursor-progress assertion (abort and alert if the cursor does not advance); per-order try/catch with a dropped-order counter surfaced in health; first-run cursor seed per D-2; `?`/`&` handling in the URL. *(M4, M5, M6)*
4. **Validation loosened to the spec.** `reason` accepted as free text (it is informational); a `rejected` counter for anything genuinely unparseable, visible on the bridge card. *(M7)*
5. **SKU key made consistent** — one normalisation shared by JS and SQL, plus a **unique** index and a collision report. *(M8)*
6. **`discontinued` preserved** across movements. *(M9)*
7. **Migration-skew branch** on the movements handler so deploy state B refuses loudly (`503`) instead of answering `200` with empty lists. *(M10)*
8. **Migrations split** into idempotent ALTER-only and data-only files. *(B4)*
9. **New guards:** failure-injection on the movements path (kill between statements, assert the retry applies exactly once); a poller test driving pages, a stuck cursor, a store 500, and a poison-pill order; a schema test asserting every NOT NULL column receives a bound value.

### v1.39.1 — Signature access model · *per D-1*

Document-scoped signature route, leave/claim/doc print paths moved onto it, an audit row per fetch, and a guard that asserts an unauthorised role **receives 403** — not merely that the route exists.

### v1.40.0 — Tab and navigation integrity

Register "Web Orders" in all five registries; give it an icon; fix the Sales-override blank screen; reconcile `payroll_export`↔`PAYROLL_PROC`, `Users`, and `task_reports`↔CEO; make the task-report submit surface its own failure; correct the tab-access card's false promise; **one new guard asserting `ALL_TABS` parity across every registry**, which would have caught all of M11 by itself.

### v1.40.1 — Release integrity

Probe set updated for 0075+; `DEPLOY.bat` version gate fixed; post-deploy version assertion in `deploy-api.sh`; `sql-schema-check` added to the API build; `bm-coverage` tab list derived from `ALL_TABS` instead of hardcoded; registry-parity guard for migrations and crons; `AUTO-DEPLOY.md` counts corrected; Node version pinned (`engines` + `.nvmrc`) — two guards currently rely on Node ≥ 22.18 type-stripping with no pin.

## 7. What went right

Worth recording, because it is why the audit found what it found rather than production finding it:

- **The guards caught two real mistakes during the build** — a hardcoded client domain (`brands-guard`) and a wrong threshold assertion — before either shipped.
- **The idempotency key, the three-list protocol, and the "silence means retry" contract are implemented correctly**, and the store's stock path cannot double-deduct (`UNIQUE(source, event_id)` is real and enforced by the database).
- **The poller genuinely never touches stock**, statically asserted — feed C cannot double-restock what feed B already returned.
- **The token-scoped public signature route survived review** — 32-hex validation, DB-backed lookup, a fixed role allowlist so the R2 key cannot be traversed, and revocation works.
- **Every degradation path for a pending migration was already handled on the read side**, so a migrations-behind deploy degrades visibly rather than 500-ing — with the one write-side exception now recorded as M10.
